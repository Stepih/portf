# Аудит проекта portfolio (showmyworks.ru)

Дата: 2026-10-07. Ветка `design-sync`. Аудит сделан по рабочей копии вместе с незакоммиченными изменениями (см. раздел «Состояние рабочей копии»).

## Как проводился аудит
- **Прочитан весь код:** `src/` (все `.ts`, `.tsx` и ключевые `.scss`), конфиги, `package.json`, `package-lock.json`, `.design-sync/`, содержимое `public/`, индекс git. Поведение двух библиотек сверено с их исходниками в `node_modules`.
- **Что запускалось:**
  - `npx tsc --noEmit` — **0 ошибок**;
  - `npm audit --omit=dev` — **22 уязвимости**: 1 critical, 17 high, 3 moderate, 1 low;
  - `npm audit fix --dry-run` — предпросмотр исправлений;
  - GET-запросы к уже запущенному локальному dev-серверу (`/api/albums`, `/api/media-content`, `/api/music-history`);
  - замер размеров медиафайлов.
- **Что не запускалось:**
  - `next build`: на порту 3000 работал dev-сервер проекта, а сборка перезаписала бы его `.next`;
  - линтер: ESLint не установлен;
  - тесты: их нет;
  - `docker build`: Dockerfile вне репозитория.
- **Пометки статуса:**
  - **код** — проверено чтением кода;
  - **запуск** — подтверждено запуском или измерением;
  - **предположение** — вывод, который ещё нужно подтвердить.
- **Серьёзность:**
  - **критично** — исправить в первую очередь;
  - **важно** — заметно влияет на пользователей, безопасность или поддержку;
  - **желательно** — качество и мелкие дефекты.
- Медиаконтент (треки, видео, картинки) по просьбе владельца не оценивался: всё, что лежит в `public/`, считается нужным.

## Безопасность

### S1. Токен Telegram-бота в исходном коде — критично
- **Где:** `src/app/api/sendMessage/route.ts:24-25` (`telegramBotToken`, `chatId`). Файл закоммичен, токен есть в истории git.
- **Что не так:** секрет хранится в коде. Репозиторий приватный, но токен доступен всем, у кого есть клон, доступ к GitHub-аккаунту или к образу Docker.
- **Чем грозит:** с токеном можно писать от имени бота, читать входящие сообщения бота (`getUpdates`) и менять его настройки.
- **Как исправить:**
  1. Перевыпустить токен: @BotFather → `/revoke`.
  2. Читать `process.env.TELEGRAM_BOT_TOKEN` и `process.env.TELEGRAM_CHAT_ID`. Локально значения лежат в `.env.local` (уже в `.gitignore`), в проде передаются как env контейнера.
  3. Добавить `.env.example` без значений.
  4. Если переменных нет, логировать ошибку и отвечать клиенту 500.

  Для приватного репозитория переписывать историю необязательно: после перевыпуска старый токен бесполезен.
- **Статус:** код.

### S2. Уязвимые версии Next.js и транзитивных зависимостей — критично
- **Где:** `package.json:17` (`"next": "^15.1.4"`), установлена версия 15.1.6 (`package-lock.json:3882`).
- **Что не так:** `npm audit --omit=dev` относит `next` к уровню **critical**. Среди уязвимостей:
  - RCE в протоколе React Flight (GHSA-9qr9-h5gf-34mp, она же CVE-2025-66478);
  - DoS для Server Components (GHSA-mwv6-3258-q52c, GHSA-h25m-26qc-wcjf);
  - утечка исходников Server Actions (GHSA-w37m-7fhw-fmv9);
  - уязвимости Image Optimizer;
  - всего около 30 бюллетеней.

  High-уязвимости есть также в `lodash`, `postcss`, `sharp`, `svgo`, `picomatch`, `nanoid` и других.
- **Чем грозит:** сайт публичный и работает на App Router, поэтому RCE означает выполнение кода в контейнере без авторизации. DoS-уязвимости позволяют положить сайт.
- **Как исправить:** `npm audit fix` без `--force`. Предпросмотр: `next 15.1.6 → 15.5.27`, `lodash 4.17.21 → 4.18.1`, `sharp 0.33.5 → 0.35.5`, всё в пределах текущих semver-диапазонов. Вместе с этим обновить `react`/`react-dom` до последнего 19.x.
  - Что останется после этого:
    - `music-metadata` (через `file-type`) — исправление требует мажорной v12. Парсятся только собственные файлы, риск низкий.
    - `next-sitemap` (через `braces`/`fast-glob`) — работает только при сборке на доверенных данных. Можно отложить.
- **Статус:** запуск (`npm audit`, `npm audit fix --dry-run`).

### S3. `/api/sendMessage` открыт для злоупотреблений — важно
- **Где:** `src/app/api/sendMessage/route.ts`.
- **Что не так:**
  - Входные данные проверяются только на `!name || !contact` (`:19`). Нет проверки типов, длины и формата; `message` может быть любого размера.
  - Нет ограничения частоты запросов.
  - Стоит `Access-Control-Allow-Origin: *` (`:6-8`), то есть отправлять может любой сайт.
  - Ветка `if (req.method === 'OPTIONS')` (`:11-13`) никогда не выполнится: обработчик экспортирован как `POST`.
  - Текст ошибки Telegram возвращается клиенту (`:45-47`).
  - Тип `any` (`:37`, `:45`).
- **Чем грозит:** личный Telegram можно завалить спамом с любого домена или скрипта. Сообщение длиннее 4096 символов Telegram отклонит, и клиент получит 500 с внутренним текстом ошибки.
- **Как исправить:**
  - Проверять, что значения — строки, обрезать пробелы и ограничить длину: имя ≤ 50, контакт ≤ 30, сообщение ≤ 2000.
  - Добавить скрытое поле-honeypot.
  - Простой in-memory rate-limit по IP: для одного контейнера достаточно `Map` с окном, например не больше 5 запросов в 10 минут.
  - Убрать CORS-заголовки: форма отправляется с того же домена.
  - Клиенту отдавать общее сообщение об ошибке, подробности писать в лог.
- **Статус:** код.

### S4. Форма отправляет заявки на прод-домен — важно
- **Где:** `src/app/popup/components/popup/Popup.tsx:38`, вызов `fetch('https://showmyworks.ru/api/sendMessage')`.
- **Что не так:** URL абсолютный. Из-за `CORS: *` (S3) запрос проходит и с `localhost`.
- **Чем грозит:** любая проверка формы при разработке отправляет реальную заявку в прод-бот. При смене домена форма сломается.
- **Как исправить:** `fetch('/api/sendMessage')`.
- **Статус:** код.

### S5. Пакет-опечатка `saas` в зависимостях — желательно
- **Где:** `package.json:23`, `"saas": "^1.0.0"`.
- **Что не так:** это пустой пакет: в `node_modules/saas` есть только `package.json`. Скорее всего, его поставили по опечатке вместо `sass`, который тоже есть в зависимостях.
- **Чем грозит:** если владелец пакета опубликует версию 1.x с вредоносным `postinstall`, она установится автоматически (supply-chain).
- **Как исправить:** удалить из зависимостей.
- **Статус:** код.

## Баги и потенциальные ошибки

### B1. Страницы получают данные через `http://localhost:3000` — критично
- **Где:** `src/app/music/page.tsx:14` и `:28`, `src/app/media/page.tsx:12`.
- **Что не так:** серверные компоненты делают HTTP-запрос к route handlers того же приложения по жёстко заданному адресу. `fetch` с `revalidate` делает страницы статическими с ISR, то есть они пререндерятся при `next build`.
- **Чем грозит:**
  - При сборке, например на этапе `docker build`, сервера на `localhost:3000` нет, и `fetch` падает. Ошибку ловит `try/catch` в странице, поэтому страница успешно пререндерится **в состоянии ошибки**: «Ошибка загрузки треков» и пустая история на `/music`, текст ошибки вместо контента на `/media`.
  - Такая версия отдаётся, пока ISR не перегенерирует страницу: на `/music` это первый запрос спустя 100 с, на `/media` — спустя 1 с.
  - Если процесс в контейнере слушает не порт 3000, страницы сломаны постоянно.
  - Каждая регенерация — лишний HTTP-запрос к себе.
- **Как исправить:**
  - Вынести логику в серверные функции `src/lib/content/{albums,musicHistory,mediaContent}.ts` и вызывать их прямо из страниц, задав `export const revalidate = …`.
  - Route handlers оставить тонкими обёртками над теми же функциями, если API нужен снаружи.
- **Статус:** код. Поведение при сборке — предположение по семантике Next 15, подтвердить в REFACTOR_PLAN, шаг 0.2.

### B2. Регистр в импорте стилей Breadcrumbs — важно
- **Где:** `src/components/breadCrumb/BreadCrumb.tsx:6` импортирует `'./Breadcrumbs.module.scss'`, а файл (и запись в индексе git) называется `BreadCrumbs.module.scss`.
- **Чем грозит:** на регистрозависимой ФС (Linux, сборка внутри Docker) будет `Module not found`, и сборка упадёт. На Windows и macOS ошибка не проявляется.
- **Как исправить:** привести импорт к имени файла.
- **Статус:** код (импорт и индекс git). Почему прод сейчас собирается — предположение: видимо, сборка идёт на регистронезависимой ФС.

### B3. Клик по альбому перетирает состояние play/pause — важно
- **Где:** `src/app/music/PlayMusic/album/Album.tsx:35`: `onClick={() => { handleAlbumSelect(album); statusPlay.setPlay(statusPlay.play) }}`.
- **Что не так:** обновления состояния применяются по порядку, и последний вызов `setPlay(statusPlay.play)` возвращает старое значение.
- **Чем грозит:**
  - повторный клик по текущему альбому не переключает воспроизведение: `prev => !prev` из `handleAlbumSelect` перезаписывается;
  - если трек стоял на паузе, выбранный новый альбом тоже остаётся на паузе: `setPlay(true)` перезаписывается на `false`.
- **Как исправить:** удалить `statusPlay.setPlay(statusPlay.play)`.
- **Статус:** код.

### B4. Глобальная блокировка скролла без гарантированного снятия — важно
- **Где:**
  - `src/scripts/scrollTo.ts:30-44` (`bodyLock`/`bodyUnLock`);
  - вызовы: `Steps.tsx:52-60`, `MediaContentList.tsx:27-30`, `PlayMusicClient.tsx:75-87`, `ImageMediaContent.tsx:124`, `scrollTo.ts:6-21`.
- **Что не так:**
  - Блокировку ставят несколько независимых компонентов; при размонтировании никто её не снимает.
  - В `ImageMediaContent.tsx:124` вызов стоит прямо в теле рендера, то есть это побочный эффект на каждом рендере, включая каждый кадр скролла (см. P2).
  - Таймер снятия в `scrollToElementById` не отменяется.
- **Чем грозит:** уход со страницы при открытом списке треков или во время «пошаговой» прокрутки истории может оставить `overflow: hidden` на `body`, и следующая страница перестанет скроллиться. `MediaContentList` вызывает `bodyUnLock` по клику «На главную», то есть проблема известна и залатана точечно.
- **Как исправить:** хук `useBodyScrollLock(active)` со счётчиком активных блокировок и снятием в cleanup эффекта; убрать вызовы из рендера.
- **Статус:** код. Сценарий «застрявшего» скролла в браузере не воспроизводился — предположение.

### B5. Нарушения Rules of Hooks — важно
- **Где:**
  - `src/components/slider/Slider.tsx:41`: `if (content === undefined) return` стоит до `useState`.
  - `src/components/breadCrumb/BreadCrumb.tsx:15-17`: `return null` до `usePathname()`.
- **Чем грозит:**
  - Slider: если `content` меняется между `undefined` и массивом, React падает с ошибкой «Rendered more/fewer hooks».
  - Breadcrumbs сейчас не падает только потому, что `usePathname` — это голый `useContext` (`node_modules/next/dist/client/components/navigation.js:110-115`). Любое изменение внутри Next или включение React Compiler это сломает.
  - Ширина окна в Breadcrumbs вычисляется через JS, поэтому на десктопе крошки мелькают после гидратации.
- **Как исправить:** перенести хуки выше ранних `return`. Breadcrumbs скрывать CSS-медиазапросом `@media (min-width: 560px)` вместо `window.innerWidth`.
- **Статус:** код.

### B6. Метрика не считает переходы между страницами — важно
- **Где:** `src/app/template.tsx:12` (незакоммиченное изменение) и библиотека `next-yandex-metrica`.
- **Что не так:** библиотека отслеживает навигацию через `Router.events` из `next/router` (`node_modules/next-yandex-metrica/dist/hooks/useTrackRouteChange.js:4,12`). Это API Pages Router, в App Router эти события не генерируются. Кроме того, провайдер стоит в `template.tsx`, а template перемонтируется на каждой навигации.
- **Чем грозит:** в статистику попадает только страница входа. Клиентские переходы, например с главной на `/music`, не учитываются, поэтому поведенческие данные занижены.
- **Как исправить:**
  - Свой клиентский компонент в `layout.tsx`: скрипт инициализации через `next/script` один раз и `useEffect` по `usePathname()` + `useSearchParams()` → `ym(ID, 'hit', url)`.
  - ID вынести в константу (сейчас он повторяется 4 раза: `template.tsx:12`, `ButtonStandartSize.tsx:32,67`, `ButtonSmallSize.tsx:23`).
- **Статус:** код (исходник библиотеки).

### B7. Вспышка светлой темы при загрузке — желательно
- **Где:** `src/components/header/SelectThemeButton.tsx:18-35`.
- **Что не так:** тема читается из `localStorage` только после гидратации, а эффект `[theme]` сначала ставит `light`.
- **Чем грозит:** у пользователей тёмной темы на каждой полной загрузке мелькает светлая.
- **Как исправить:**
  - inline-скрипт в `<head>` (`layout.tsx`), который ставит `data-theme` до отрисовки;
  - `suppressHydrationWarning` на `<html>`;
  - начальное состояние кнопки брать из `document.documentElement.dataset.theme`.
- **Статус:** код.

### B8. Плеер: эффекты, таймеры и необработанные промисы — желательно
- **Где:** `src/app/music/PlayMusic/player/Player.tsx`, `commands/Command.tsx`, `PlayMusicClient.tsx`.
- **Что не так:**
  - `setTimeout` вызывается прямо в теле рендера (`Player.tsx:78-83`): новый таймер на каждый рендер в первую секунду, очистки нет.
  - Эффект `[volume, statusPlay, isAudioReady]` (`Player.tsx:112-117`) срабатывает на каждый рендер родителя, потому что `statusPlay` пересоздаётся (`PlayMusicClient.tsx:27-30`).
  - Промис `audio.play()` не обрабатывается (`Player.tsx:115`, `Command.tsx:24`).
- **Чем грозит:** если браузер заблокирует автовоспроизведение, будут ошибки `Uncaught (in promise)`, а интерфейс покажет «играет», хотя звука нет. Плюс лишние вызовы `play()`.
- **Как исправить:**
  - таймер перенести в `useEffect` с очисткой;
  - `play().catch(() => setPlay(false))`;
  - зависеть от `isPlaying`, а не от объекта `statusPlay`.

  Полностью — см. A2.
- **Статус:** код.

### B9. Кнопки «вперёд»/«назад» на краях альбома переключают play — желательно
- **Где:** `src/app/music/PlayMusic/player/commands/Command.tsx:17-18`.
- **Что не так:** на последнем треке «вперёд», а на первом «назад» вызывают `setPlay(!play)`, хотя кнопки стилизованы как неактивные (`unsetActive`).
- **Как исправить:** на краях ничего не делать или переходить к первому/последнему треку.
- **Статус:** код.

### B10. Неверный порядок треков — желательно
- **Где:** `src/app/api/albums/route.ts:11`, `:54`. Используется `readdirSync` без сортировки, а Node возвращает имена в побайтовом порядке.
- **Что не так:** в альбоме «2022» треки идут так: `1, 10, 11, 2, 3, …, 9`. Кроме того, при ошибке чтения длительность возвращается как `'0'`, а не `'0:00'` (`:32`).
- **Как исправить:** натуральная сортировка `a.localeCompare(b, 'ru', { numeric: true })` для альбомов и треков; в fallback вернуть `'0:00'`.
- **Статус:** запуск (ответ `/api/albums`).

### B11. Линия прогресса трека — желательно
- **Где:** `src/app/music/PlayMusic/player/commands/LineTrack.tsx`.
- **Что не так:**
  - При `duration = 0` ширина считается как `NaN%` (`:116`).
  - Перемотка реализована только на событиях мыши (`:51-72`): на тач-экранах перетаскивание не работает.
  - Компонент типизирован как `FC<any>` (`:5`).
- **Как исправить:** защита от деления на 0; Pointer Events вместо mouse; типизировать пропсы.
- **Статус:** код.

### B12. `/media` прокручивает страницу наверх при ресайзе — желательно
- **Где:** `src/app/media/components/ImageMediaContent.tsx:76-79`.
- **Что не так:** `updatePositions()` вызывает `window.scrollTo({ top: 0 })` при монтировании и при каждом изменении высоты окна больше чем на 100px.
- **Чем грозит:** при повороте планшета или изменении размера окна пользователь теряет позицию на странице.

## Производительность

### P1. `/api/albums` читает все аудиофайлы на каждый запрос — важно
- **Где:** `src/app/api/albums/route.ts:27-28` (`fs.readFileSync` целиком + `parseBuffer`), `:11`, `:54` (`readdirSync`).
- **Что не так:**
  - GET-обработчики в Next 15 не кэшируются. Каждый запрос синхронно читает **все** треки (`public/music` занимает 154 МБ) и парсит их.
  - Чтение запускается внутри `map(async …)` до первого `await`, поэтому все буферы живут одновременно, и пиковая память на один запрос близка к размеру всей папки.
  - Локальный замер на dev-сервере: **0,42 с** первый запрос, **0,15 с** повторный. Всё это время event loop заблокирован.
- **Чем грозит:** несколько параллельных запросов к публичному `/api/albums` (боты, сканеры) нагружают CPU и память контейнера и тормозят остальные запросы. Это простой вектор DoS.
- **Как исправить:**
  - Кэш на уровне модуля (ключ — `mtime` папки), асинхронный `fs.promises`.
  - `parseFile(path, { duration: true })` вместо чтения файла целиком.
  - Альтернатива — генерировать JSON-манифест при сборке.
  - Сделать вместе с B1: страница будет вызывать функцию напрямую.
- **Статус:** код + запуск (время, размер папки).

### P2. Скролл на `/media` перерисовывает весь список — важно
- **Где:** `src/app/media/components/ImageMediaContent.tsx:50-52`, `:94-98` (`setScrollPosition` на каждом `requestAnimationFrame`), `:124` (`bodyUnLock` в рендере). То же в фоне: `src/components/bg-page/Background.tsx:28-31` (`setParallax` на каждое событие `scroll`, компонент живёт в layout на всех страницах).
- **Что не так:** каждый кадр скролла вызывает setState, React перерисовывает все `MediaItem` вместе со слайдерами и ещё пишет стили `body`.
- **Чем грозит:** рывки при прокрутке на слабых устройствах, лишняя нагрузка на CPU и батарею.
- **Как исправить:** `useScroll` + `useTransform` из framer-motion (он уже подключён): прозрачность и параллакс обновляются без ре-рендера React.
- **Статус:** код. Величину просадки FPS не измеряли.

### P3. Видео в «истории» загружаются целиком — важно
